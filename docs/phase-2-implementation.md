## 1. Architecture overview

```
Browser
  │  ① form submit / page load
  ▼
Next.js 16 (App Router)
  │  src/middleware.ts      ← cookie-based redirect guard
  │  src/context/AuthContext.tsx  ← in-memory token + user state
  │  src/lib/api.ts         ← fetch wrapper that injects Bearer token
  ▼
FastAPI backend  (port 8000)
  │  /auth/*   ← login, register, refresh, me
  │  /trips/*  ← trip CRUD
  │  /trips/{id}/waypoints/*  ← waypoint CRUD
  ▼
PostgreSQL (async SQLAlchemy + asyncpg)
```

Two tokens travel in different ways:

| Token | Transport | Lifetime | Purpose |
|---|---|---|---|
| Access token (JWT) | `Authorization: Bearer` header | 15 min | Authenticate every API request |
| Refresh token (JWT) | httpOnly `SameSite=Strict` cookie, path `/auth/refresh` | 30 days | Silently get a new access token |

The access token lives only in JavaScript memory (never `localStorage`) so it is invisible to other browser tabs and disappears on page close. The refresh cookie is httpOnly so JavaScript cannot read it at all — only the browser sends it automatically to `/auth/refresh`.

## 2. Backend — data model

### Files

- `backend/app/models/user.py` — `User`
- `backend/app/models/trip.py` — `Trip`, `Waypoint`
- `backend/app/models/__init__.py` — re-exports all three so Alembic's `target_metadata` can discover them

### User

Passwords are never stored in plain text. The `hashed_password` column stores a bcrypt hash produced by `passlib`. See [§4 auth system](#4-backend--auth-system) for details.

`updated_at` is managed by a PostgreSQL trigger (defined in the migration) rather than application code, so it is always accurate even if a row is updated by a DB admin or a future migration script.

### Trip

Two mutually exclusive modes share the same table:

```
mode = 'point_to_point'  →  end_address / end_lat / end_lng must be set
mode = 'radius'          →  max_drive_minutes must be set
```

These rules are enforced at **three layers**:

1. **Pydantic** (`TripCreate.validate_mode_fields`) — returns a 422 with a clear message before the DB is touched.
2. **DB CHECK constraints** — the migration adds two constraints so the invariant holds even if code is bypassed (e.g. a direct SQL update).
3. **SQLAlchemy model** — the constraints are declared in `__table_args__` so they appear in any future autogenerated migration.

### Waypoint

Waypoints on a trip are ordered by an integer `position` column (0-based). A `UNIQUE(trip_id, position)` constraint prevents duplicates. The application code is responsible for keeping positions contiguous after a delete or reorder.

## 3. Backend — database migration

### File

`backend/alembic/versions/0002_phase2_auth_and_data_model.py`

### Why a hand-written migration?

Autogenerate requires a live database. This migration was written by hand so it can be reviewed and committed without needing the DB running. It is safe to run repeatedly — the enum creates use `checkfirst=True`.

### What it creates

1. PostgreSQL `ENUM` types `trip_mode` and `trip_status`
2. `users` table with indexes and a `updated_at` trigger
3. `trips` table with FK → `users`, check constraints, indexes, and a `updated_at` trigger
4. `waypoints` table with FK → `trips`, unique constraint, and index

The shared trigger function `update_updated_at_column()` is created once and reused by both `users` and `trips`.

### Applying the migration

```bash
# From the backend directory, with the DB running:
alembic upgrade head
```

### Rolling back

```bash
alembic downgrade 0001
```

The `downgrade()` function drops triggers first, then tables (in reverse FK order), then types.

## 4. Backend — auth system

### Files

- `backend/app/core/security.py` — hashing and JWT helpers
- `backend/app/core/deps.py` — FastAPI dependency that resolves the current user

### Password hashing (`security.py`)

`passlib` with the `bcrypt` scheme handles hashing and verification. The `CryptContext` handles algorithm upgrades transparently if you ever switch from bcrypt to argon2.

```python
hash_password("secret")         # → "$2b$12$..."
verify_password("secret", hash) # → True
```

### JWT creation (`security.py`)

Both access and refresh tokens are signed HS256 JWTs. They each include a `"type"` claim (`"access"` or `"refresh"`) so an attacker cannot use a refresh token as an access token or vice versa.

```python
create_access_token(str(user.id))   # 15-min JWT, type=access
create_refresh_token(str(user.id))  # 30-day JWT, type=refresh
```

`decode_token(token, expected_type)` raises `jose.JWTError` on any failure (expired, bad signature, wrong type). The callers catch this and return 401.

### Current user dependency (`deps.py`)

```python
async def get_current_user(credentials, db) -> User:
    ...
```

This is a FastAPI dependency injected via `Depends`. It:

1. Reads the `Authorization: Bearer <token>` header using FastAPI's `HTTPBearer`.
2. Decodes and validates the JWT.
3. Loads the `User` row from the database.
4. Returns the `User` object, or raises `HTTP 401` at any failure step.

The alias `CurrentUser = Annotated[User, Depends(get_current_user)]` lets endpoints declare the requirement concisely:

```python
async def get_trip(trip_id: uuid.UUID, current_user: CurrentUser, db: DB):
    ...
```

## 5. Backend — API endpoints

### Auth (`backend/app/api/auth.py`)

| Endpoint | What it does |
|---|---|
| `POST /auth/register` | Creates a user, returns access token in body + sets refresh cookie. Returns 409 if email exists. |
| `POST /auth/login` | Verifies credentials, same response shape as register. |
| `POST /auth/refresh` | Reads the httpOnly refresh cookie, issues new token pair (token rotation). |
| `GET /auth/me` | Returns the current user's profile. Requires valid access token. |

The refresh cookie is scoped to `path="/auth/refresh"` — the browser only sends it on that exact path, so it does not leak to other endpoints.

### Trips (`backend/app/api/trips.py`)

All endpoints require auth. Ownership is verified by adding `Trip.user_id == current_user.id` to every query. Trips belonging to other users return **404** (not 403) to avoid leaking whether an ID exists.

The list endpoint is paginated via `page` / `page_size` query params. Trips are returned newest-first.

### Waypoints (`backend/app/api/waypoints.py`)

Waypoints are nested under a trip. Every endpoint first checks that the parent trip exists and is owned by the current user.

**Reorder endpoint** (`POST /trips/{id}/waypoints/reorder`): accepts a list of all waypoint IDs in the desired order. It validates that the submitted IDs are exactly the set of existing waypoint IDs (no extras, no missing), then reassigns positions in a single transaction. This keeps positions contiguous with no gaps.

**Delete endpoint**: when a waypoint is deleted, all waypoints with a higher position are decremented by 1 in the same transaction, maintaining contiguous 0-based ordering.

## 6. Frontend — auth state

### File

`frontend/src/context/AuthContext.tsx`

### What it stores

```typescript
interface AuthState {
  user: AuthUser | null;    // profile fetched from GET /auth/me
  accessToken: string | null;  // in-memory only, never persisted
  isLoading: boolean;       // true while the mount-time refresh is in flight
}
```

### Session hydration on page load

When the app first mounts, `AuthProvider` fires a `POST /auth/refresh` with `credentials: "include"`. The browser automatically sends the httpOnly refresh cookie. If the cookie is valid, a new access token comes back, `GET /auth/me` is called to populate the user profile, and `isLoading` becomes `false`. If there is no valid cookie, the user is unauthenticated.

This means a user who closes and reopens the tab is automatically signed back in for up to 30 days — without ever reading a cookie from JavaScript.

### Token sync with the API client

Every time the token changes (login, register, refresh, logout), `setApiToken()` from `src/lib/api.ts` is called so the fetch wrapper always has the current token. This is a simple module-level variable — no context drilling needed for the API layer.

### `useAuth` hook

```typescript
const { user, login, register, logout, isLoading } = useAuth();
```

Throws if called outside `AuthProvider`. Components use `isLoading` to avoid flashing unauthenticated UI while the session check is in flight.

## 7. Frontend — API client

### File

`frontend/src/lib/api.ts`

### Changes from Phase 1

The Phase 1 client was a thin fetch wrapper. Phase 2 adds:

1. **`setApiToken(token)`** — stores the current access token in a module-level variable.
2. **Automatic Bearer injection** — every request reads `_accessToken` and adds the header if present.
3. **`credentials: "include"`** — ensures cookies are sent on cross-origin requests (needed for the refresh cookie path).

### Usage

```typescript
// Authenticated request — token is injected automatically
const trips = await api.get<PaginatedTrips>('/trips');

// The token is set by AuthContext after login/register/refresh
import { setApiToken } from '@/lib/api';
setApiToken(accessToken);
```

## 8. Frontend — pages

### Login (`/login`) and Register (`/register`)

Both pages are standalone full-screen forms (no `TopNav`). They:

1. Validate inputs client-side with **Zod** before hitting the API.
2. Call `useAuth().login()` or `useAuth().register()`.
3. Redirect to `/trips` on success.
4. Display field-level errors from Zod and server-level errors from the API response.

The `noValidate` attribute on the `<form>` disables browser built-in validation so Zod's messages are shown instead.

### Trips list (`/trips`)

Fetches `GET /trips` on mount and renders a list of `TripListItem` rows. Three states are handled: loading (skeleton), error (message), empty (call-to-action), and populated (list).

### New trip (`/trips/new`)

A multi-section form. The mode selector (Point-to-Point vs Radius) controls which fields are shown:

- **Point-to-Point**: shows end address + coordinates fields.
- **Radius**: shows max drive time field.

Zod schemas (`pointToPointSchema`, `radiusSchema`) are chosen at submit time based on the selected mode. On success, the user is redirected to the new trip's detail page.

## 9. Frontend — route protection

### File

`frontend/src/middleware.ts`

Next.js middleware runs on the Edge before any page is rendered. It cannot read the httpOnly cookie value (that would defeat the purpose), but it **can** check whether the cookie exists using `request.cookies.has("refresh_token")`.

| Path | No refresh cookie | Has refresh cookie |
|---|---|---|
| `/trips/*` | Redirect → `/login?next=<path>` | Allow |
| `/login`, `/register` | Allow | Redirect → `/trips` |

The `?next=` parameter is set so a future enhancement can redirect back to the originally requested page after login.

This is a **best-effort** guard. The backend is the authoritative enforcer — a missing or expired refresh cookie causes the access token refresh to fail, and the API returns 401. The middleware just provides a better UX by not rendering the page at all.

Note: the middleware can only check cookie **presence**, not cookie **validity**. A user with an expired or tampered refresh cookie will pass the middleware check and reach the `/trips` page, but the mount-time `POST /auth/refresh` in `AuthProvider` will fail and the user will end up unauthenticated. The API will then return 401 on any data request. This is expected behaviour — correctness is enforced by the backend, not the edge.

## 10. How a request flows end-to-end

### First visit (not logged in)

```
1. User opens /trips
2. middleware.ts: no refresh_token cookie → redirect to /login
3. User fills login form, submits
4. AuthContext.login() → POST /auth/login
5. FastAPI: verifies password, creates JWT pair
6. Response: { access_token } in body + Set-Cookie: refresh_token (httpOnly)
7. AuthContext: stores access_token in memory, calls setApiToken()
8. AuthContext: calls GET /auth/me to populate user profile
9. router.push('/trips')
10. middleware.ts: refresh_token cookie now exists → allow
11. /trips page mounts, calls api.get('/trips')
12. api.ts: injects Authorization: Bearer <access_token>
13. FastAPI: CurrentUser dep decodes JWT, loads User from DB
14. Returns paginated trip list
```

### Return visit (token expired, cookie still valid)

```
1. User opens /trips
2. middleware.ts: refresh_token cookie exists → allow
3. AuthProvider mounts, isLoading = true
4. POST /auth/refresh with cookie → new access_token
5. GET /auth/me → user profile
6. isLoading = false, user is set
7. /trips page renders and fetches normally
```

### Return visit (cookie expired)

```
1. User opens /trips
2. middleware.ts: no refresh_token cookie → redirect to /login
```

## 11. Running locally

```bash
# 1. Start the Docker stack (Postgres + backend + frontend)
docker compose up

# 2. Apply migrations (first time, or after a schema change)
docker compose exec backend alembic upgrade head

# 3. The app is now available at:
#    Frontend: http://localhost:3000
#    Backend API docs: http://localhost:8000/docs
```

Environment variables needed in `backend/.env`:

```
DATABASE_URL=postgresql+asyncpg://postgres:postgres@db:5432/travel_planner
SECRET_KEY=<a long random string — change this before any real deployment>
```

The `SECRET_KEY` is used to sign JWTs. Changing it in production invalidates all existing tokens.

## 12. Common pitfalls

### "All my trips disappeared" after changing SECRET_KEY

JWT signatures are tied to the secret. Changing it invalidates all existing access and refresh tokens. Users will need to log in again.

### 422 when creating a radius trip

`max_drive_minutes` is required. The Pydantic validator on `TripCreate` catches this before hitting the DB. Make sure to send it in the request body when `mode` is `"radius"`.

### 401 on every request after page reload

This usually means the mount-time refresh failed (no valid cookie). Check that the backend is running and reachable at `NEXT_PUBLIC_API_URL`, and that the refresh cookie is being set (check DevTools → Application → Cookies).

### Middleware redirects even after successful login

The middleware only checks cookie presence, not validity. If the backend sets the cookie with `secure=True` but you are on plain HTTP in dev, the browser will silently drop it. The current implementation sets `secure=False` for local dev.

### Waypoint positions have a gap after a delete

This should not happen — the delete endpoint decrements all subsequent positions in the same transaction. If you see gaps, check that no raw SQL is bypassing the API.
